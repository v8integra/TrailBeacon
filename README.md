# TrailBeacon

A World of Warcraft: Forever addon for placing, customizing, sharing, and navigating to custom map and minimap markers.

## Status

Early development. Currently implemented:

- Minimap button — drag around the minimap ring to reposition; left-click opens the world map, right-click opens the marker list. (No coordinate readout on the button itself — the Forever beta added a native one to the minimap, so TrailBeacon's own copy was removed.)
- Map view marker toolbar — bottom bar on the world map with a row of icon-type buttons: Herb, Ore, Quest, Danger, Trash Mob, Heal, Food, Cooking, Home, Marker (final art, see "Art assets"). Click an icon to arm it, then click the map to drop a marker; right-click the armed icon (or right-click anywhere on the map) to cancel placement without dropping one. Click an existing marker to open its edit menu (increase/decrease size, change color, lock/unlock, delete); middle-click an unlocked marker to delete it directly. A "Delete All" button (with confirmation) clears every marker on the current map.
- Map view share toolbar — top bar with Select All / Deselect All / Manual Select (toggle; auto-turns off when the map closes) / Copy / Import, plus an Auto-Share checkbox. Copy opens a popup with a compact export string for selected markers; Import accepts that same string format or a pasted TomTom-style `/way` line (`/way 45.2, 67.8` or `/way #mapID 45.2 67.8`).
- Category filtering — a Filters button on the share toolbar opens a checkbox panel (one per icon type). Any combination can be shown/hidden at once; hidden categories are excluded from both pin rendering and Select All. Filter state persists via SavedVariables.
- Marker list/browser panel — right-click the minimap button to open a scrollable window listing every saved marker (icon, name, zone, coordinates). Clicking an entry opens the world map to that marker's zone; each row has a delete button. Minimap button left-click now opens the world map directly (previously a stub).
- Tracking arrow — shift-click a marker pin on the map to track it (shift-click again to untrack; tracked pins get a gold ring, same as the white selection ring but a different color). A freestanding, draggable screen arrow rotates to point at it and shows distance below, throttled to ~5 updates/sec. Fully hidden while in an instance (no partial operation, per the spec's secret-values constraint), and hidden whenever nothing is tracked. Shows a desaturated "Different Zone" state if the tracked marker isn't on the player's current map.
- Arrow options window — shift + right-click the arrow itself to open it: a full-size preview, a row of style thumbnails (one per arrow art file, highlighting the active one), size +/- controls, a grid of preset color swatches (in-window, not a separate Blizzard color-picker popup), and a grayscale toggle. The arrow itself has a dark bezel/background behind it now so it doesn't sit in empty space.
- Auto-share — when the checkbox is on, every marker *you* place is broadcast over an addon message to your party (or raid, if in one) in real time. Markers you receive this way import silently (with a chat print naming the sender) and are never themselves re-broadcast, so there's no relay/loop risk. Separate from the manual Copy/Import flow, as speced. Only triggers on locally-placed markers — importing a `/way` line or a pasted export string does not auto-share.

Every feature in [CLAUDE.md](CLAUDE.md) now has a first-pass implementation.

Note: the spec's SavedVariables draft didn't define a marker `name` field, only `iconType`/etc. — the browser currently falls back to the icon type's label (e.g. "Herb") as the display name, since there's no naming UI yet. Multiple markers of the same type will show the same name, distinguished by zone/coordinates.

**In-game testing found and fixed several real bugs, the last ones resolved by reading the actual Forever-branch Blizzard source** (`Gethe/wow-ui-source`, referenced in this file's own notes) instead of guessing from memory:

- The XML pin template originally loaded before the Lua file defining its mixin (TOC order), and separately was missing `virtual="true"` — without it, a named XML `<Frame>` is just a one-off instantiated frame, not a reusable `CreateFrame(...)` template. Both fixed.
- Once the template registered, `AcquirePin` still failed with `assertion failed!` — turned out `AcquirePin` (see `MapCanvas_DataProviderBase.lua`) wires up `OnMouseUp`/`OnEnter`/`OnLeave` scripts *itself*, asserting those slots are still empty first. My XML was pre-claiming them. Fixed: dropped the `<Scripts>` block, added `enableMouseMotion="true" enableMouseClicks="true"` to the template (what actually tells `AcquirePin` to wire the scripts up), and renamed the override methods to what Blizzard's mixin actually calls — `OnClick` for clicks, `OnMouseEnter`/`OnMouseLeave` for hover (not `OnEnter`/`OnLeave`).
- Both toolbars were anchored to `WorldMapFrame` itself, but `WorldMapFrame`'s own bounding box includes its title bar/window chrome (`BorderFrame` covers the whole thing) — the actual map viewport is `WorldMapFrame.ScrollContainer`, anchored *below* the title area. That's why the top bar sat above the map under the title bar, and why windowed mode (different chrome than maximized) threw off the width. Reparented both to `ScrollContainer` and raised their frame strata to `"HIGH"`, which also fixed the bottom toolbar's missing background/text (it was a z-order issue — the map's own content was drawing over the backdrop and text while the interactive icon buttons, which get their own frame level, still showed through).
- The minimap button and the AddOn list were never actually wired up to use the final icon art (`Media/Icon/TrailBeaconIcon.tga`) — still referenced a stock Blizzard icon path that may not even resolve in this build (hence the blank minimap circle). Fixed, and added `## IconTexture` to the TOC for the AddOn list icon. (The icon itself has no background fill, so it reads as transparent on the minimap — a source-art thing, not a code thing.)
- Markers appeared to "follow" between different map views, and Select All/Deselect All/clicking a pin to edit it all looked unresponsive. Root cause: `RemoveAllData` (called at the top of every `RefreshAllData`, i.e. every map change *and* every marker-state-changing action) is a no-op stub on `MapCanvasDataProviderMixin` - consumers are expected to override it. I never had, so old pins were never released back to the pool; every refresh just acquired more pins stacked on top of the stale ones from whatever map/state was previously showing. Fixed by overriding `RemoveAllData` to call `self:GetMap():RemoveAllPinsByTemplate(PIN_TEMPLATE)`.
- Markers were sometimes invisible over explored terrain. `MapCanvas_PinFrameLevelsManager.lua` shows pins default to a fixed frame-level baseline (2000) that other map content can register above; I'd never set one. Added an `OnLoad` that calls `UseFrameLevelType("PIN_FRAME_LEVEL_TOPMOST")` — a reserved keyword that always resolves above everything else currently registered, regardless of what specific layer was covering them.
- Clicking a marker pin threw a Lua error (`attempt to call a nil value`) — `EasyMenu`/`UIDropDownMenu` don't exist anywhere in this build's source at all; Blizzard has fully replaced them with a new `Blizzard_Menu` addon (`MenuUtil`/`Menu`). Rewrote the marker context menu against the real `MenuUtil.CreateContextMenu` API (verified in `MenuUtil.lua` and `Menu.lua` — `rootDescription:CreateButton(...)` returns the button's element description, which is what `:SetEnabled(...)` needs for the locked-marker disabled state). `Blizzard_Menu` loads first and is always available, so no load-order risk here.
- Placement mode (arm an icon, click the map): clicking the armed icon a second time to toggle it off wasn't actually working, so that's simplified to two distinct actions now — click an icon to arm it, right-click (the icon itself, or anywhere on the map) to cancel. Tooltip wording matched to state, too ("Click to select" on unselected icons, "Right-click to deselect icon" on the armed one).
- Ctrl + right-click to delete a marker conflicted with Blizzard's own native right-click-to-drop-a-waypoint-pin feature on the map (their pin still got placed underneath). Tried Shift + right-click next, but pins pass *any* right-click through to the map beneath them regardless of modifier (so players can still zoom out or drop a waypoint even near a pin) - it zoomed the map out instead. Switched to middle-click instead, which isn't subject to that passthrough.
- Layout tweaks from testing feedback: Manual Select no longer appends ": On" to its own button text (was overflowing the button — it's highlight-only now, like a toggle), the share toolbar is inset further from the map's left/right edges to clear a Blizzard button it was overlapping (exact button not yet identified — flag which side if it's still overlapping), the marker toolbar moved up to clear Blizzard's native coordinate readout at the bottom of the map, and its icon buttons have more spacing between them.
- The tracking arrow pointed roughly 180° off (not exactly, varying a bit with which way the player was facing when tested). Checked both `GetPlayerFacing()` and `Texture:SetRotation()` against warcraft.wiki.gg instead of assuming: both are confirmed 0 = north/no-rotation with **positive = counter-clockwise**. My original formula measured the world bearing toward east at +90° (a clockwise-style convention) while combining it with facing's counter-clockwise convention — opposite handedness, which produces exactly this kind of "close to 180 but drifting with facing angle" error. Fixed by measuring bearing toward west at +90° instead, matching `GetPlayerFacing()`'s own convention directly. That brought it down to a small, consistent ~10-20° residual offset (likely from the one still-unverified piece, WoW's world-position axis assumption itself) — calibrated out with a `ROTATION_OFFSET` of 15° in [Modules/TrackingArrow.lua](Modules/TrackingArrow.lua). Adjust that value directly if it still drifts.

Keep testing and reporting anything that still looks wrong.

The color/tint picker on the arrow options window multiplies the texture's own colors (`SetVertexColor`) — since the arrow art is full-color painted work rather than a flat silhouette, tinting it will shift/muddy its colors rather than cleanly recoloring it. Leaving color at white (the default) avoids this; worth revisiting if that turns out to matter in practice. Marker category icons don't have this problem — see "Art assets" below.

## Art assets

- `ArrowImages/` — first-pass raw source exports (7 racial-themed arrows + the addon icon), kept for reference. Had a fake checkerboard baked into opaque RGB instead of real alpha, and the icon had a glow-halo artifact — both fixed in the next pass.
- `ArrowImages/ArrowsNoBG/` — second-pass source: re-exported with a proper background-removal tool (real alpha this time) and manually squared (content centered, transparent-padded to make width == height).
- `Media/Arrows/*.{png,tga}` and `Media/Icon/*.{png,tga}` — game-ready versions built from the `ArrowsNoBG` sources: alpha edges smoothed (the bg-removal tool left a hard, jagged/aliased cutout with almost no anti-aliasing — confirmed by sampling, then fixed with a small blur on just the alpha channel), cropped to content with a small margin, resized to 512px (256px for the icon) via Lanczos. All square now, matching the source canvases — verified the "narrowing" didn't distort the art (content aspect ratio in the new files matches the old non-square processed versions; the squaring was done by adding side padding, not by squeezing pixels). Both known issues from the first pass are resolved: no checkerboard bleed-through anywhere, and the icon's lantern glow no longer has a halo artifact around it.
- `icons/` — the 10 marker-category icons as supplied (flat, solid black line art, 128x128, real alpha already). Kept as-is for reference.
- `Media/Icons/*.{png,tga}` — the same 10 icons with RGB forced to pure white (alpha untouched). They were solid black, and the marker system's "Change Color" tint (`SetVertexColor`, a multiply) has no effect on black — 0 × anything is still 0. White is the correct base for that mechanism to actually work, and since these were already flat single-color art, converting to white lost no detail. Mapped to categories in `Modules/Markers.lua`'s `TB.ICON_TYPES`: `leaf`→Herb, `pickaxe`→Ore, `star`→Quest, `skull-crossbones`→Danger, `trash`→Trash Mob (marks raid/dungeon filler mobs), `bandage-wound`→Heal, `hamburger-soda`→Food, `knife-kitchen`→Cooking, `home`→Home, `marker`→Marker (general-purpose, no specific use).

## Installation (development)

Clone or symlink this folder into your WoW `Interface/AddOns` directory as `TrailBeacon`, then enable it at the character select screen.
